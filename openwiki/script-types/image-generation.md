# Image Generation Scripts

Scripts in `image-gen/` run inside the mPCC image builder while an OS image (Rocky/RHEL-family, `dnf`-based) is generated. Their output is baked into the image: services, mounts, users, and config symlinks. They read context from `/tmp/mprov/entity.json` per the [entity.json contract](../architecture/overview.md#the-entityjson-contract); the jobserver/script-runner installs, `setup_data_share_mount.sh`, and `run_ansible.sh` all validate that file up front (`[ -s ]` plus a `jq -e 'type == "object"'` check) and exit nonzero before writing anything if it or a value they need is missing — partially-configured images are worse than failed builds.

## mProv jobserver installs

Two scripts install the pip package `mprov_jobserver` in different roles, each writing configs under `/etc/mprov/` (chmod 600 because they embed the `apikey`) and a systemd unit:

- **`install_mprov_jobserver.sh`** — a *secondary/edge jobserver* for image and repo distribution. Job modules: `image-sync` (image dir `/export/images`), `mprov-webserver`, `image-delete`. A 0.7.0+ job server unpacks itself into every image it builds — a bundle with its own Python at `/usr/libexec/mprov` — before image-gen scripts run (mprov_jobserver#309), and the image's system pip can't install 0.7.0 (it needs Python 3.11, mprov_jobserver#311), so the script prefers the bundle: if `/usr/libexec/mprov/bin/python3` exists, it skips pip and takes the version and plugin configs from the bundle's own package; otherwise (0.6.x images) it installs via system pip, intentionally unpinned (fixes reach images only through new releases), and logs the version it finds either way (#24, #87). It copies the package's default plugin configs from wherever the package lives (the path varies across Python versions, and without them the webserver has no `rootDir` and serves `/`), exiting with an error if they're missing, then overwrites `image-sync.yaml` with the local image dir. This is what enables the mPCC's "redirection" to distributed jobservers. `post-boot/enable_and_run_jobserver.sh` later enables the service and opens firewall port 8080 (`tests/test_install_jobserver.py` covers the bundle preference and the plugin-config copy).
- **`install_mprov_script-runner.sh`** — installs the `script-runner` module that executes image-gen and post-boot scripts, or the `nads` module when `entity.json`'s `slug` is `nads` (the node auto-detection image). The guard reads `slug` *before* requiring a non-empty `apikey`, because the job server has deliberately sent an empty `apikey` for the public `nads` image since 2022 (#84 — an earlier unconditional non-empty check exited before the slug was ever read, breaking NADS installs). The service is `Type=oneshot` with `mprov_jobserver -d -r -s -b -c /etc/mprov/<mod>.yaml` and is enabled (not started) so it runs at boot — this is the bootstrap that lets post-boot scripts run at all.

Both install scripts also support **certificate-authenticated builds** (mprov_control_center#381, mprov_scripts#98/#100). When `entity.json` carries a `tls` object (see [entity.json contract](../architecture/overview.md#the-entityjson-contract)) the job server is building with its own certificate and hands over an empty `apikey`, the mPCC's https URL, a 2-hour build credential (`tls.cert`/`tls.key`, deleted before packing), and the mPCC's CA (`tls.ca`). In that mode both scripts accept the empty key for every image, write **no apikey** into their configs, install only `tls.ca` into the image as `/etc/mprov/mpcc-ca.crt` with `caBundle` set to it — so nodes without a certificate of their own can still verify the mPCC — and never let `tls.cert`/`tls.key` reach the image. They also rewrite the stored `mprovURL` to the mPCC's **plain-HTTP** URL (`http_url()`: same host with IPv6 kept in brackets, port 80, same path, no query — the mirror of the `https_url()` rule), because the mPCC's `genNetworkInterfaces.py` fetches `<mprovURL>/enroll/ca.crt` before the node trusts anything, and a NADS node never can; every node client moves to https itself once it holds a node certificate. Shared-key builds are unchanged whatever the URL. `tests/test_install_tls.py` covers cert mode for both scripts.

## Certificate renewal timer

- **`install_mprov_cert_renew.sh`** — from mPCC 0.7.0 a node enrolls at boot and gets its own certificate in `/etc/mprov/tls` (mprov_control_center#381/#506). This script downloads the mPCC's helper from `<mprovURL>static/mprov_enroll.py` to `/usr/libexec/mprov/mprov_enroll.py` — verifying with `entity.json`'s `tls.ca` when the job server handed one over — and installs `mprov-cert-renew.service` (oneshot `mprov_enroll.py renew` after `network-online.target`, on the job server's bundled Python or the system `python3`; nothing `Wants=` it, so a failure never holds up boot) plus `mprov-cert-renew.timer` (`OnBootSec=5min`, `OnUnitActiveSec=1d`, `RandomizedDelaySec=1h`, `Persistent=true`, enabled). `renew` is a no-op on a node without a certificate; otherwise it asks the mPCC on every run (mprov_control_center#532): the mPCC renews the certificate in its own renewal window, and if it revoked the certificate the node re-enrolls through the window an admin opened for it ("Let these systems re-enroll"). The helper comes from the mPCC, so an image built by an older mPCC carries that mPCC's copy, which only renews a certificate in its last 14 days and doesn't notice a revocation. A pre-0.7.0 mPCC 404s on the helper: the script then installs nothing and exits 0, so the entry can sit in an image's script list before the mPCC is upgraded; any other download failure, or a fetched file that isn't the helper, fails the build. The node certificate it keeps current is what `localTempDisk.py` and the other node clients authenticate with (see [Post-Boot Scripts](post-boot.md#node-identity-and-hardware-configuration)); `tests/test_install_cert_renew.py` covers the 404/success/failure paths.

## NFS data share mount

- **`setup_data_share_mount.sh`** — installs `nfs-utils` and appends an fstab entry mounting `${shareHost}:/export/data` at `/data`. The guard inspects the *mount-point field* (`awk '$2 == "/data"'`), so a comment or another export that merely mentions `/export/data` doesn't suppress the entry, and it pads a missing final newline first so the entry can't be glued onto an unterminated last line. The NFS server is chosen by `config_params.mprovDataShareHost` — settable on the OS distro, a system group, or the image, e.g. the mPCC's name on an IB or other cluster network — and defaults to the mPCC host parsed out of `mprovURL` (any `:port` is stripped, since it isn't part of an NFS server name).

`setup_mprov_share_mount.sh` (mounting `${mpccHost}:/export/mprov` at `/opt/mprov`) and `create_slurm_client_service.sh` were **removed** because they depended on the mPCC's `/export/mprov` share; Slurm client setup is no longer part of this repo's image-gen catalog.

## Ansible runner

`run_ansible.sh` (registered for **both** script types in `mpcc_scripts.yaml`) lets users extend provisioning with Ansible instead of shell:

- Installs `ansible` from EPEL, detects run mode from `entity.json` (`slug` present → image-gen, else post-boot).
- Extracts `config_params` from `entity.json` into `variables.json` as the extra-vars file.
- Selects the Ansible **collections**, **roles**, and **playbooks** to run via a single `ansible_list` `jq` helper. When the mPCC serves merged lists — newer mPCCs (mprov-ng/mprov_control_center#269) put the inherited slugs (distro → system groups → image → system, deduped, in inheritance order) into `config.ansiblecollections` / `config.ansibleroles` / `config.ansibleplaybooks` — the script walks those slugs and looks each one up in `entity.json` for its URL and type; a slug present in `config` but absent from `entity.json` is warned about on stderr and skipped. Against an older mPCC (no `config` lists) it falls back to collecting the lists from the entity's layers — systemgroups, the entity itself, and the OS distro. Both paths then filter to entries whose `scriptType.slug` starts with the run mode, and tolerate the list keys being missing at any level.
- Installs collections/roles with `ansible-galaxy`, runs each role against localhost through a generated `/tmp/role.yaml` wrapper, then `wget`s and runs each playbook locally **in the order the list provides** (only playbooks that actually downloaded). Cleans up `/tmp/mprov/ansible/` afterward.

Note the roles are executed in list order with implicit gathering; playbook URLs are fetched with `wget -N`, so mPCC-hosted playbook URLs must be reachable from the node/image build. `tests/test_run_ansible.py` exercises both selection paths (merged `config` slugs and layer fallback) with the ansible commands stubbed.

## Package scripts

- **`extra_packages.sh`** — installs `config_params.extra_packages`, accepted either as a JSON array or a space-separated string; a missing/null/empty value installs nothing. Names are split into a bash array before `dnf` so a package name is never glob-expanded.
- **`install_yq.sh`** — installs Go (if `rpm -q golang` fails) then `github.com/mikefarah/yq/v4` pinned to `YQ_VERSION` (currently `v4.53.3`) into `/usr/local/bin` via `go install`, which checks the module against the Go checksum database. The pin exists because `@latest` made each image build pick a different yq; bump the version variable to upgrade. EPEL has no yq for Rocky 8, so `go install` is used on both major versions. `tests/test_install_yq.py` covers the pin.
- **`ansible-playbooks/`-style payloads**: `post-boot/ansible-playbooks/nvidia-fm-install.yaml` is an example playbook consumed by the runner (see [Post-Boot Scripts](post-boot.md#slurm-and-gpu-configuration)).

`image-gen/set_root_pw.sh` and `image-gen/setup_ssh.sh` were removed; configure the root password and authorized SSH keys through the OS distro's Root Password and Root SSH Keys, which the jobserver applies at image build.

## Changing this area

- Config-param handling is covered by the pytest suite in `tests/` (see [Architecture Overview](../architecture/overview.md#the-entityjson-contract)): an unset or `null` param must take the script's documented default, never the string `null`. Run `python -m pytest tests` (needs Docker) when touching scripts that read `config_params`.
- Jobserver configs embed the mPCC `apikey` — never log or copy `/etc/mprov/*.yaml` contents into docs or issues. In certificate mode the same discipline applies to `tls.cert`/`tls.key`: only `tls.ca` may be written into the image (`/etc/mprov/mpcc-ca.crt`).
